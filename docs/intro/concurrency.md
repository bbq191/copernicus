# Copernicus 多任务并发执行模型

> 本文分析多个转写/纪要任务同时提交时的资源竞争行为、瓶颈定位与推荐策略。
> 所有结论均基于代码中的锁机制与信号量配置推导，适用于单 GPU 单进程部署。

---

## 一、并发模型概述

Copernicus 的任务执行基于 asyncio 协程调度。每个任务在提交时立即创建一个后台协程，但协程的推进受各阶段资源锁的约束，因此"并行提交"≠"并行执行"。

Pipeline 按以下顺序依次经历各阶段：

```
音频预处理 → ASR 推理 → 说话人平滑 → LLM 文字纠错 → LLM 摘要评估
```

各阶段的并发属性不同，下表给出汇总：

| Pipeline 阶段 | 并发机制 | 实际并发数 | 瓶颈资源 |
|---|---|---|---|
| 音频预处理（ffmpeg） | 无锁 | 无上限 | CPU / 磁盘 IO |
| ASR 推理 | 全局互斥锁（1 把） | **1** | GPU 显存 |
| 说话人平滑 | 无锁 | 无上限 | CPU |
| LLM 文字纠错 | 全局信号量（3 槽） | **≤ 3 路 LLM 请求** | Ollama 推理队列 |
| LLM 摘要评估 | 同上，共享同一信号量 | **≤ 3 路（含纠错）** | Ollama 推理队列 |

---

## 二、各阶段竞争详解

### 2.1 ASR 阶段 — 全局串行

ASR 推理阶段持有一把进程内全局互斥锁，所有任务（无论是标准纪要还是纯转写）共享同一把锁。

竞争行为：

- 锁持有方：正在执行 GPU 推理的任务
- 锁等待方：已完成音频预处理、等待进入 ASR 的所有其他任务
- 等待期间：等待任务的协程挂起，不占用 CPU，不阻塞事件循环

等待队列增长规律：

```
任务数   ASR 队列等待时间（以单任务 ASR 耗时 T 为单位）
  1          0
  2          ~T
  3          ~2T
  N          ~(N-1)×T
```

**第 N 个任务在 ASR 阶段的等待时间随任务数线性增长。**

### 2.2 LLM 纠错/评估阶段 — 共享全局信号量

`OllamaClient` 是单例，其内置的全局信号量（容量 = `LLM_MAX_CONCURRENT`，默认 3）对所有上层调用方可见：纠错、评估、合规审核、TTS 改写均通过同一信号量排队。

纠错阶段的内部并发：每个任务的纠错逻辑内部也维护一个局部信号量（容量 = `CORRECTION_MAX_CONCURRENCY`，默认 3），但它只控制单任务发出的批次数，最终仍须通过全局信号量实际发送请求。

多任务叠加时的有效并发：

```
任务数   同时处于纠错/评估阶段   全局 LLM 并发路数（上限）
  1               1                       3
  2               2                       3（两任务共享，无法各占 3）
  N               N                       3（无论多少任务叠加，上限不变）
```

**LLM 吞吐量不随并发任务数增加。** Ollama 本地推理为单进程单 GPU，信号量控制的是 HTTP 连接数，GPU kernel 层面依然是串行的，主要作用是隐藏网络/调度延迟。

## 三、多任务时序图

以 2 个任务同时提交为例，展示各阶段的实际重叠情况：

```
时间轴 ──────────────────────────────────────────────────────►

Task A  [音频预处理]──[  ASR 推理（独占 GPU）  ]──[纠错·LLM]──[评估·LLM]
                                                    │                │
Task B     [音频预处理]──[等待 ASR 锁]──[ ASR 推理 ]──[纠错·LLM]──[评估·LLM]
                                                         ↑              ↑
                                            A 纠错与 B ASR   A 评估与 B 纠错
                                            不竞争（不同资源）  共享 LLM 信号量(3)
```

以 3 个任务同时提交为例：

```
Task A  [预处理]──[ASR]────────────────────────[纠错]──[评估]
Task B  [预处理]──[等锁]──[ASR]────────────────[纠错]──[评估]
Task C  [预处理]────[等锁]──────────[ASR]──────[纠错]──[评估]
                                                └───── 3 个任务的纠错和评估
                                                       共享 3 路 LLM 槽位
```

**可以真正并行的**：
- 所有任务的音频预处理（CPU/IO 密集，互不干扰）
- 排在 ASR 队列中的任务等待期间，不阻塞系统其他操作

**无法并行的**：
- 任意两个任务的 ASR 推理
- 超过 3 路并发的 LLM 请求

## 四、VRAM 视角

多任务并发时，VRAM 占用并不随任务数线性增长，因为 ASR 是串行的：

```
单任务运行时 VRAM 占用（峰值）：

  [ASR 阶段]   ASR 模型 ~4.5 GB + 激活值 ~1 GB = ~5.5 GB
  [纠错阶段]   ASR 卸载前：ASR 模型 ~4.5 GB + Ollama LLM ~4–8 GB（视模型而定）
               keep_alive=0 时 LLM 推理结束后立即释放，峰值约 8–13 GB

  [评估阶段]   同纠错阶段，ASR 已完成可能仍驻留
```

两个任务并发时 VRAM 峰值与单任务相同，因为 ASR 不同时运行。

**关键约束**：ASR 与 TTS 不能同时运行。合规审核阶段会主动卸载 ASR（释放 ~4.5 GB），为 14B LLM 腾出空间。

## 五、内存（RAM）视角

每个任务在 Pipeline 各阶段的主要内存对象：

| 阶段 | 主要内存对象 | 典型大小（1 小时 MP4） | 释放时机 |
|---|---|---|---|
| 文件上传 | 原始文件字节 | ~300 MB | AudioPreprocess 完成后立即释放 |
| 音频预处理 | 临时 WAV 文件（磁盘） | ~115 MB（磁盘） | ASR 完成后由 AudioService 清理 |
| ASR 推理 | ASR 结果段落列表 | < 1 MB | Pipeline 结束后随任务一起 GC |
| LLM 纠错 | 批次文本字符串 | < 1 MB/批 | 批次完成后 GC |
| LLM 评估 | 全文字符串（≤ 50,000 字） | < 0.5 MB | 任务完成后 GC |

**多任务并发时的 RAM 峰值**（N 个任务同时处于文件上传/预处理阶段）：

```
峰值 ≈ N × 单文件大小
```

- 2 个 300 MB 文件同时上传：峰值约 600 MB
- 5 个 300 MB 文件同时上传：峰值约 1.5 GB

文件字节在音频预处理完成后即释放，不会在 ASR 或 LLM 阶段持续占用。

## 六、推荐并发策略

### 最优流水线并发数：2–3 个任务

```
理由：
  - 第 1 个任务做 ASR 时，第 2 个可以完成音频预处理，ASR 锁释放后立即接上
  - 第 1 个任务进入纠错时，第 2 个开始 ASR，两者使用不同资源，GPU 无空闲
  - 第 3 个任务可以在前两个任务交替占用 ASR 时提前完成预处理
```

2 个任务并发时的 GPU 利用率最优：

```
GPU 利用率
  1 个任务：ASR → 空闲 → ASR 不可能，因为串行
  2 个任务：Task A ASR → Task B ASR（紧接着），GPU 几乎无空闲
  3 个任务：同上，轻微收益，但 LLM 槽位竞争加剧
```

### 不建议超过 5 个并发任务

| 并发任务数 | ASR 队列深度 | 末尾任务额外等待（以单 ASR 约 10 分钟计） | 风险 |
|---|---|---|---|
| 2 | 1 | ~10 min | ✅ 正常 |
| 3 | 2 | ~20 min | ✅ 可接受 |
| 4 | 3 | ~30 min | ⚠️ 后提交任务体验下降 |
| 5 | 4 | ~40 min | ⚠️ 接近任务超时边界 |
| 6+ | 5+ | ~50 min+ | ❌ 可能触发 3600s 任务超时 |

## 七、调优方向

### 方向一：提升 LLM 纠错吞吐（`OLLAMA_KEEP_ALIVE`）

当前 `OLLAMA_KEEP_ALIVE=0`，每批次纠错请求发出后 Ollama 卸载模型，下一批重新加载（约 2–5 秒冷启动/批）。

多任务并发时，各任务的纠错批次交替触发模型 load/unload，累计开销显著。

建议在任务密集期将保活时间设置为与任务持续时间匹配的值：

```ini
# .env（任务密集期配置）
OLLAMA_KEEP_ALIVE=300
```

代价：LLM 模型在任务间隙占用约 4–8 GB 显存。需确认 VRAM 预算充足。

### 方向二：ASR 批处理（架构改造）

当前瓶颈在于 ASR 全局互斥，改造方向是将多个待处理音频合批一次 GPU 推理。这需要修改 Pipeline 的调度层，将成本较高，可评估后决定是否投入。

### 方向三：单独的任务类型路由

合规审核（`compliance_audit`）在执行时会主动卸载 ASR 模型，若与转写任务交替执行，会产生 ASR load/unload 循环，代价较高。建议通过时间窗口将合规审核与转写任务错开提交。
